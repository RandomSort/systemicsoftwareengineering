# Right and Wrong

Source piece: `bookofnull/pieces/029-is.md` (four koan questions).
Companion pieces: `007-customer-is-user.md`, `037-expectations.md`.

## Core argument

Four parallel questions — a correct answer the user didn't understand, a
question that got the wrong answer, a feature the user uses wrong, a tool
you use wrong — each asking whether the artifact was "right". The cumulative
argument: correctness is not an intrinsic property of answers, features, or
tools. It is a property of the *interaction* between the artifact and a
human. An output can be locally correct and systemically wrong. The
companion piece (007) sharpens it: "the user always does it wrong / the
customer is always right" — the same person, judged by two different frames.

## Extracted claims

- **Definitional:** "right" for an artifact is defined at the sociotechnical
  boundary: right answer = answer that produced understanding; right
  feature = feature that produced the intended outcome in use.
- **Empirical:** users "misusing" a feature is information about the design,
  not (only) about the users — consistent with Norman's affordance framing
  and the HCI maxim that the user is not wrong. (/enrich target.)
- **Normative:** evaluate engineering work by realized outcomes in use, not
  by delivered outputs; a shipped-but-misused feature counts as a wrong
  feature.
- **Normative (037):** "Never break the users' expectations" — expectations,
  not specifications, are the contract that matters.

## Framework relevance

Core material for an outcomes-over-outputs concept and for drawing the
system boundary to include the humans: a "systemic" software engineering
that stops at the API is measuring the wrong system. Creates a productive
tension with pure-correctness views (tests pass, spec met, therefore right).

## Quotable

- "If you built the feature / And the user is using it wrong / Was it the right feature?"
